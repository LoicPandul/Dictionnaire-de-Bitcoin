Entier de 0 à 65535, placé dans le champ `kind` d'un événement Nostr, qui indique la nature de cet événement. Un kind dit aux clients comment lire le reste de l'événement : le kind `0` porte le profil de l'utilisateur, le kind `1` une note courte, le kind `3` sa liste de suivi, le kind `9735` un reçu de zap. Selon la plage dans laquelle il tombe, il dit aussi aux relais comment conserver l'événement.

Le sens des autres champs dépend du kind. Pour un kind `0`, le champ `content` contient un objet JSON avec le nom, la description et l'image de l'utilisateur ; pour un kind `1`, il contient le texte de la note ; pour un kind `3`, il ne sert pas et la liste tient dans les tags. Le même tag peut ainsi changer de sens d'un kind à l'autre : NIP-01 cite le tag `r`, qui n'a pas la même signification dans une note et dans une liste de relais (kind `10002`). Chaque NIP peut définir de nouveaux kinds qui n'ont pas encore de sens ailleurs : NIP-01 définit le kind `0`, NIP-10 décrit aujourd'hui le kind `1`, présent dès le premier NIP-01, NIP-02 le kind `3`, NIP-57 les kinds `9734` (demande de zap) et `9735` (reçu de zap).

NIP-01 répartit les kinds en 4 catégories selon leur plage, qui indiquent la façon dont un relais les garde :

* réguliers (`1`, `2`, `4` à `44`, `1000` à `9999`) : les relais sont censés tous les stocker ;
* remplaçables (`0`, `3`, `10000` à `19999`) : pour un même auteur et un même kind, le relais doit garder la version la plus récente et peut écarter les précédentes (voir ÉVÉNEMENT REMPLAÇABLE) ;
* éphémères (`20000` à `29999`) : les relais les transmettent aux abonnés du moment et ne sont pas censés les stocker ;
* adressables (`30000` à `39999`) : le relais doit garder la dernière version pour chaque combinaison d'auteur, de kind et de valeur du tag `d` (voir ÉVÉNEMENT ADRESSABLE).

Les plages `45` à `999` et `40000` à `65535` ne relèvent d'aucune de ces conventions. NIP-01 précise d'ailleurs qu'il s'agit de conventions, et que les implémentations de relais peuvent s'en écarter.

Prenons un exemple. Alice met à jour la description de son profil : son client publie un nouvel événement de kind `0`. Comme ce kind est remplaçable, les relais gardent le nouveau profil d'Alice et peuvent écarter l'ancien. Le même jour, elle publie 2 notes de kind `1`, que les relais sont censés garder toutes les 2. Quand son client s'authentifie auprès d'un relais selon NIP-42, il signe un événement de kind `22242`, de la plage éphémère ; NIP-42 précise que le relais le vérifie mais ne doit le transmettre à aucun client. Le kind sert enfin aux requêtes : un client qui ne veut que les notes et leurs republications (kind `6`, NIP-18) demande au relais un filtre `{"kinds": [1, 6]}`.

Aucune autorité n'attribue formellement les kinds. Le dépôt des NIP en tient un index de fait, mais personne n'est obligé de s'y conformer. Le README du dépôt des NIP tient une table des kinds connus, en précisant qu'elle n'est pas exhaustive, et renvoie à un registre lisible par machine (`registry-of-kinds`) ou à tout registre alternatif au même format. Rien n'empêche donc 2 applications d'utiliser le même numéro pour des usages différents ; la table et les NIP sont là pour l'éviter.

Dans le NIP-01 tel qu'il est versé en mai 2022 dans le dépôt des NIP (le texte existait depuis novembre 2020 dans le dépôt principal de Nostr), il n'existait que 3 kinds de base : `0` (`set_metadata`), `1` (`text_note`) et `2` (`recommend_server`, qui recommandait un relais), ce dernier ayant depuis quitté NIP-01 (en août 2023) puis la table du dépôt, où il figurait comme déprécié. Les plages à partir de 10000 viennent de NIP-16, proposé par Semisol en mai 2022 pour les événements remplaçables et éphémères, et de NIP-33, ajouté en janvier 2023 pour les événements remplaçables paramétrés (aujourd'hui adressables). Les 2 documents sont fusionnés dans NIP-01 le 13 août 2023.

*Le terme anglais* kind *est employé tel quel en français ; on parle par exemple d'un « événement de kind `1` », noté aussi `kind:1`.*
