Set of hashes that makes it possible to verify that a transaction is included in a block, from that block's header alone. For each level of the block's Merkle tree, the proof contains the sibling hash of the one being carried up, all the way to the root. A few hundred bytes thus replace downloading all the transactions of the block. See Merkle tree for the structure itself.

Let's take an example. Alice uses a light wallet and Bob tells her he has just paid her. The wallet keeps only block headers, 80 bytes each, whose Merkle root summarizes all the transactions of the block. It asks a full node for the proof of Bob's transaction. The node returns the block header, the position of the transaction in the block, and the list of sibling hashes. The wallet starts from the txid, concatenates it with the first sibling hash, on the side dictated by the position, and applies a double `SHA256` to obtain the node of the next level up. It repeats the operation level by level. If the final hash equals the Merkle root in the header, the transaction belongs to the block. It remains to verify that the header is part of the chain with the most proof of work, and to count the blocks that follow it.

The proof contains one 32-byte hash per level of the tree, so its size grows with the logarithm of the number of transactions. For a block of 4,096 transactions, which has 12 levels above the leaves, it comes to 384 bytes.

Bitcoin Core has included this mechanism since version 0.8.0, released in February 2013: Pieter Wuille wrote the `CPartialMerkleTree` class on October 27, 2012. `BIP-0037` uses it for the `merkleblock` message, which contains not a branch but a partial tree: the header, the number of transactions in the block, a list of hashes, and a sequence of bits that indicates, walking the tree from the root, which nodes lead to a sought transaction. A single message thus proves the inclusion of several transactions. The `gettxoutproof` RPC returns a proof in this format, and `verifytxoutproof` checks it: it recomputes the root, compares it to the one in the header, then makes sure the block is in the active chain. On the wallet side, `bdk_electrum` has fetched Merkle proofs and headers along with transactions since BDK #1489, and validates that they are in confirmed blocks. The idea goes back to the 2008 white paper, whose section 8 describes simplified payment verification (SPV) based on the “Merkle branch” that links a transaction to its block.

A Merkle proof has limits. It establishes the inclusion of a transaction, never its absence: BIP-0037 notes that a node can still lie by omission. It also says nothing about the validity of the transaction, only that a miner included it in a block.

The construction of the tree also opens up flaws. When a level has an odd number of nodes, the last one is duplicated before the next level is computed: two different transaction lists, [1, 2, 3, 4, 5, 6] and [1, 2, 3, 4, 5, 6, 5, 6], then give the same root (CVE-2012-2459). Bitcoin Core detects this case in `ComputeMerkleRoot`. CVE-2017-12842 targets proof verifiers directly: a 64-byte transaction, excluding witness data, has the size of an internal node formed of two 32-byte hashes and can be read as either one. An attacker can thus fool an SPV wallet with an inclusion proof for a transaction that is not in the block. According to Bitcoin Optech (September 6, 2024), the risk also affects sidechains that do SPV and could affect some proposed covenants.

`BIP-0054` lists three countermeasures that need no consensus change: also requesting the proof of the coinbase transaction to deduce the depth of the tree, rejecting any proof in which an internal node is also a valid serialization of a transaction, or requiring internal nodes in single `SHA256`. Eric Voskuil puts the first at 576 bytes more on average for a typical modern block. BIP-0054, championed by Antoine Poinsot, prefers to invalidate 64-byte transactions, so that verifiers have no countermeasure to apply. Sergio Demian Lerner had suggested in 2018, among other options, that the header commit to the depth of the tree. In the debate reported by Optech in September 2024, Voskuil sees no justification for the invalidation for full nodes, and Poinsot acknowledges that his argument about caching invalid blocks was wrong; the remaining argument concerns software that verifies Merkle proofs. The discussion was ongoing at the date of the newsletter.

*The white paper says “Merkle branch” and BIP-0037 says “partial merkle tree.” The proof, which concerns a transaction, should not be confused with the Merkle tree that makes it possible.*
