Spending mode for a P2TR output in which the spender reveals one of the scripts committed to by the output, proves that it is part of the output, then satisfies it. It contrasts with key path spending, which needs only a signature (see KEY PATH).

The locking script of a P2TR output boils down to version 1 and a 32-byte public key, the output key. It is obtained by tweaking an internal key with the root of a Merkle tree (see MERKLE TREE) in which each leaf is a script accompanied by a version number. The output thus commits to all its possible scripts without showing any of them. The script path is used when the key's signature is not available, for example for lack of agreement between the parties, or when the funds must be spent under the condition of a script.

The witness of the spending input contains the data that the chosen leaf's script needs, that script, and then, as the last element (excluding the annex, if any), the control block (see CONTROL BLOCK). This block carries the leaf version and the parity of the output key's y-coordinate in its first byte, then the 32-byte internal key, then the Merkle path: the hashes of the sibling nodes that link the leaf to the root. It measures $33 + 32m$ bytes, where $m$ is the depth of the leaf and is at most 128. Each node computes the hash of the revealed leaf (tagged hash `TapLeaf`), combines it with each hash in the path (`TapBranch`) to obtain a root, applies the tweak to the internal key, and checks that the result is the output key, parity included. If the comparison fails, the spend is invalid. Otherwise, the node looks at the leaf version. For leaf version `0xc0`, it applies the Tapscript rules (see TAPSCRIPT). Other leaf versions are not yet defined: spending them succeeds without execution, and Bitcoin Core refuses to relay such a spend.

Let's take the example from BIP-0341, a tree of 5 leaves A, B, C, D, and E, where AB denotes the node that joins A and B. Alice wants to spend via script D, which sits 3 levels below the root. Her control block contains the version and parity byte, the internal key, then the hashes of C, of E, and of AB, for $33 + 3 \times 32 = 129$ bytes. Scripts A, B, C, and E stay hidden: the blockchain shows only the hashes of C, of E, and of AB.

This mode has a privacy cost. According to BIP-0341, a script path spend reveals that a script path existed and that the key path was not applicable. The depth of the leaf also gives information, including the minimum depth of the tree. Reusing a leaf in several outputs can also make the same Merkle branches reappear in the proof of another spend. On the relay side, Bitcoin Core (version read at commit `db0bde16b9`) treats as non-standard a Taproot spend that includes an annex, as well as a script path spend in which a stack element exceeds 80 bytes for a `0xc0` leaf. The key path has no size limit of this kind.

The script path is part of Taproot (BIP-0341, with the script rules of BIP-0342), activated at block 709,632. BIP-0341 recommends providing an unspendable script path even when none is wanted, so that a malicious party cannot add one without the others' knowledge in an aggregated key. The P2MR proposal (BIP-0360) removes the key path and keeps only this one (see P2MR).

*Not to be confused with the locking script (`scriptPubKey`) of a P2TR output, which boils down to version 1 and the output key: the script executed by the script path is that of a leaf of the tree.*
