Way of spending a Taproot (P2TR) output with a single Schnorr signature, valid for the output's public key, without revealing or executing any script. BIP-0341 distinguishes it from the script path (see SCRIPT PATH), the other way of spending the same output. The notion applies only to SegWit version 1 outputs whose witness program is 32 bytes, and the public key it refers to is the output key.

A Taproot output contains a single public key, the output key $Q$. It results from an internal key $P$ tweaked by a `TapTweak` tagged hash that combines $P$ and, when there is one, the Merkle root of the script tree: $Q = P + \text{int}(t)G$, where $t$ denotes this hash. At spend time, the node first removes the annex, if any, from the witness stack. If exactly one element remains, it applies the key path: that element is a Schnorr signature, which must be valid for $Q$. If at least two remain, it applies the script path. Bitcoin Core's code follows this rule in `src/script/interpreter.cpp`.

Let's take an example. Alice and Bob create a Taproot output whose internal key aggregates their two keys (see MUSIG2), with a tree that contains a fallback script. As long as they agree, they jointly produce a signature for $Q$, and the transaction's witness contains only that signature: 64 bytes, plus one byte for the signature hash type (sighash) when it is not the default type. BIP-0360 counts 66 bytes for this witness, including the number of elements and the length of the signature. An observer sees a Schnorr signature like any other. They cannot tell that an aggregated key produced it, or that a fallback script existed. If Bob disappears, Alice must resort to the script path, which reveals the script used, its Merkle proof, and the fact that the key path was not applicable.

This is why BIP-0341 writes that outputs should ideally be spent via the key path. Such a spend can be an ordinary payment from a single-key or multisignature wallet, or the cooperative settlement of a contract among several parties. The choice of internal key steers this: BIP-0341 recommends putting the most likely key there or, failing a single-key condition, an aggregation of all the keys; when no key path is wanted, it proposes a NUMS (nothing up my sleeve) point, whose private key nobody knows, preferably blinded with a random number. A wallet that needs no script, such as the one in BIP-0086, commits to an unspendable script path rather than having none at all.

When signing, Bitcoin Core first tries the key path, with the internal key and then with the output key, before moving on to the script path. To estimate the weight of a spend from a `tr(…)` descriptor, it assumes a key path, and its comments acknowledge that this can strongly underestimate the actual weight when a script is needed.

This path has a downside. The output key is public as soon as the funds are received, and anyone who recovered its private key could spend via the key path: this is the long exposure attack, which BIP-0360 invokes to propose P2MR, an output type that reuses P2TR without a key path. The P2MR witness is then larger than that of a P2TR key path spend: 135 bytes against 66 for the simplest case in BIP-0360. Also, the key path is the subject of CISA (cross-input signature aggregation): the Bitcoin Optech newsletter of August 7, 2026 summarizes a cross-input signature aggregation proposal (which the newsletter calls BIP460) that aggregates the key path spends of a new output type modeled on P2TR, and leaves script paths unchanged.

The key path dates from the Taproot soft fork, specified by BIP-0341 (Pieter Wuille, Jonas Nick, and Anthony Towns), whose rules apply starting at block 709,632.

*Sometimes written “keypath”. Not to be confused with the derivation path of an HD wallet, which also contains the word “path” in Bitcoin Core's code.*
