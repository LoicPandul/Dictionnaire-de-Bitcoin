Nostr event of kind `1` that carries a short text message, the equivalent of a post on a social network. By extension, the word also refers to the `note` identifier defined by NIP-19, which encodes the ID of an event in Bech32 so that it can be copied or shared. NIP-10 describes the kind `1` note as a plain text note (*plaintext note*): its `content` field contains human-readable text, and NIP-10 asks that no Markdown or HTML be put in it.

A note follows the path of any Nostr event. Let's take an example. Alice writes "Hello Nostr" in her client. The client builds a kind `1` event whose `content` field contains this text, computes its ID (the `SHA256` hash of the serialized event, 32 bytes written as 64 hexadecimal characters), has it signed with Alice's private key, then sends it to her relays. Bob, who follows Alice, has asked these relays for the kind `1` events whose author is Alice's public key: he receives the note, and his client verifies the signature before displaying it in his feed. Kind `1` is one of the so-called regular events, which NIP-01 expects relays to store in full, unlike replaceable events, of which only the latest version counts.

Replies are also kind `1` notes, linked to one another by tags. When Bob replies to Alice, his client adds an `e` tag that contains the ID of Alice's note, a relay where it can be found, the `root` marker, and Alice's public key, as well as a `p` tag with that same key so that Alice is notified. If Charlie then replies to Bob, his note carries 2 `e` tags: one marked `root` pointing to Alice's note, which opens the discussion, the other marked `reply` pointing to Bob's, and his `p` tags repeat those of Bob's note plus Bob's key. Thanks to these markers, any client can rebuild the thread of the discussion. A kind `1` note is used to reply only to another kind `1` note: to comment on another type of event, NIP-22 provides comments of kind `1111`. A note can also quote another by placing a `nostr:` address in its text (NIP-21 and NIP-27), accompanied by a `q` tag (NIP-18), while the simple sharing of a note without comment (a repost) goes through an event of kind `6` (NIP-18).

To designate a note outside the protocol, in a message or on a web page, its hexadecimal ID remains impractical and is easily mistaken for a key: event ID, public key, and private key are all 32 bytes. NIP-19 therefore gives them 3 distinct Bech32 prefixes: `npub` for the public key, `nsec` for the private key, and `note` for the ID of an event. The 32-byte ID `f39e9b451a73d62abc5016cffdd294b1a904e2f34536a208874fe5e22bbd47cf`, that of a note given as an example by NIP-27, is thus written `note17w0fk3g6w0tz40zszm8lm555kx5sfchng5m2yzy8flj7y2aagl8s8td87j`. Like the `npub`, this form is used only for display, input, and QR codes: in the fields and tags of events as in the requests sent to relays, the ID stays in hexadecimal.

The `note` identifier has 2 limits. It contains only the 32 bytes of the ID: a client that receives it knows which event to look for, but not on which relay, and may never find it if it is not connected to the author's relays. The `nevent` format adds relay hints, the author's key, and the kind for this purpose. Moreover, these 32 bytes say nothing about the kind of the event: despite its name, a `note` identifier does not guarantee that it designates a kind `1` note.

The text note has existed since the first text of the protocol: the version of NIP-01 that fiatjaf published on November 15, 2020 already defines kind `1`, then called `text_note`, as the text of a note, "anything the user wants to say". The `note` prefix arrived with NIP-19, added to the NIP repository on December 16, 2022. On January 13, 2025, a change proposed by Vitor Pamplona moved the definition of kind `1` from NIP-01 to NIP-10, which deals with notes and discussion threads. It cleared up a confusion: since NIP-01 is marked `mandatory`, some developers inferred that a client had to support notes.
