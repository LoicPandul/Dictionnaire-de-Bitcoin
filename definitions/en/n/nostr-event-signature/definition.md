Schnorr signature, compliant with BIP-0340 on the secp256k1 curve, that the author of a Nostr event computes over the event ID with the author's private key, and which fills the `sig` field. It lets anyone verify that the event comes from the holder of the public key given in the `pubkey` field and that it has not been modified since it was signed, without trusting the relay that forwarded it. Nostr uses the same signature scheme as Bitcoin's Taproot outputs.

The signed ID is a hash of the whole event. To obtain it, the array `[0, <pubkey>, <created_at>, <kind>, <tags>, <content>]` is written as JSON encoded in UTF-8, with no unnecessary whitespace or line breaks and with precise escaping rules for the text, then hashed with `SHA256`. The result, 32 bytes written as 64 lowercase hexadecimal characters, becomes the `id` field. The signature covers these 32 bytes, so it commits to the author, the date, the kind, the tags, and the content at once. The slightest change to any of these fields produces a different ID, and the signature is worthless for it. The serialization rule is strict so that 2 different implementations always compute the same ID for the same event.

The signature follows BIP-0340. The public key fits in 32 bytes, since only the X coordinate of the point is kept, and the signature in 64 bytes, written as 128 hexadecimal characters in the `sig` field. The author derives a secret nonce (a hash of the private key, the public key, the message, and auxiliary random data), computes the corresponding point $R$, then a challenge $e$ from $R$, the public key $P$, and the message $m$ (here the event ID) using the tagged hash `BIP0340/challenge`. The verifier recomputes the challenge, derives a curve point from the signature and the public key alone, and checks that its X coordinate is the one recorded in the signature. Since BIP-0340 recommends adding randomness when signing, 2 signatures of the same event by the same key differ when the signer supplies that randomness, and both are valid.

Let's take an example. Alice publishes a note. Her client fills in `pubkey`, `created_at`, `kind`, `tags`, and `content`, computes the ID, signs it with Alice's private key, and sends the complete event to 3 relays. Bob receives it through one of them. His client recomputes the `SHA256` of the serialization, checks that it matches the `id` field, then verifies the signature with Alice's public key. If a relay had modified a single character of the note, the hash would no longer match `id`; if it had also replaced `id`, the signature would no longer match. Bob's client, which verifies events, discards them in both cases.

The reader's client remains the verifier of last resort: from the very start, in his November 2020 introduction of Nostr, fiatjaf wrote that signatures are verified on the client side and that relays do not need to be trustworthy. A relay can also verify events before accepting them. The strfry relay, for example, recomputes the ID, then verifies the signature with `libsecp256k1`, the elliptic curve library that Bitcoin Core also uses, and rejects the event on failure. It then replies with a negative `OK` message with the `invalid` prefix, one of the prefixes that NIP-01 standardizes.

The signature proves who signed, but not when. The `created_at` field is set by the author, who can sign an event dated in the past or in the future; some relays reject dates too far from the current time, a case that NIP-01 gives as an example of an `invalid` rejection. Nor does the signature protect against loss or theft of the private key (see NSEC): anyone who holds it can sign on behalf of the user. That is why some clients delegate signing to a Nostr signer, which keeps the key away from the application. Finally, BIP-0340 recommends not using the same private key in several signature schemes: if the same key signed with deterministic ECDSA (RFC 6979) and with Schnorr using a nonce computed the same way, the 2 signatures could reveal the private key. A Bitcoin key that signs with ECDSA should therefore not be reused as a Nostr key.
