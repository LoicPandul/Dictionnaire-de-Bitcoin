Versioned encryption format defined by NIP-44, which encrypts text between 2 Nostr keys and places it in a signed event. Version 2, the only one defined, combines an ECDH key exchange on secp256k1, HKDF key derivation, padding, the ChaCha20 cipher, and an HMAC-SHA256 message authentication code. NIP-44 defines no messaging kind: it provides only the encryption, which other NIPs use (see NOSTR PRIVATE DIRECT MESSAGE and GIFT WRAP).

Alice and Bob exchange no prior secret, since each one's public key is already known. For each pair, the format first computes a conversation key: an ECDH between one party's private key and the other's public key, of which the 32-byte x coordinate is kept without hashing, then passed through HKDF-extract with `SHA256` and the salt `nip44-v2`. The result is identical in both directions. For each message, the encrypter then draws a random 32-byte nonce and derives from the conversation key, with HKDF-expand, 76 bytes split into a 32-byte ChaCha key, a 12-byte ChaCha nonce, and a 32-byte HMAC key (see ECDH and SECP256K1).

The plaintext is then padded with zero bytes to hide its exact length: 32 bytes at minimum, then steps that grow with the size, after a prefix that gives the real length (2 bytes, or 6 bytes from 65,536 bytes). The padded plaintext is encrypted with ChaCha20, then an HMAC-SHA256 is computed over the nonce followed by the ciphertext. The payload is the Base64 of the version (the byte `0x02`), the nonce, the ciphertext, and the message authentication code. A 1-byte plaintext thus becomes 99 bytes, or 132 Base64 characters, and always starts with `A`, which encodes the version byte (the next character depends on the start of the nonce). This payload goes into an event that the sender signs, in practice in its `content` field (see NOSTR EVENT SIGNATURE), and the recipient must verify the signature before decrypting.

The authors justify several choices. ChaCha replaces AES because it is faster and better resists attacks that target multiple keys; it replaces XChaCha because the latter was not standardized. HMAC-SHA256 replaces Poly1305 because polynomial message authentication codes are easier to forge. The authentication code protects the payload before the event signature, which then authenticates the whole.

NIP-44 also lists what it does not do. It offers no plausible deniability (a signature proves who wrote), no forward secrecy (if a key leaks, all past conversations can be decrypted), and no post-compromise security (future ones can be decrypted). It is not resistant to quantum computers: a CRQC (see CRQC) would break the ECDH and could decrypt the messages. It leaves the IP address visible to relays, as well as the `created_at` date and part of the message size, and it does not handle attachments. For high-risk situations, the NIP recommends a dedicated end-to-end encrypted messenger, with Nostr used only to exchange contacts.

This format replaces the one in NIP-04, which encrypted with AES-256-CBC in an event of kind `4` and appended the initialization vector after the ciphertext (`?iv=`). The 2 formats are not interchangeable: NIP-44 states that it should not be used as is in place of NIP-04 payloads. NIP-04 carries the `unrecommended` warning, first in favor of NIP-44, then of NIP-17. The plaintext size limit was 65,535 bytes; since June 28, 2026, NIP-44 accepts up to 4,294,967,295 bytes, at the cost of a 6-byte prefix from 65,536 bytes. Signers also use it (see NOSTR SIGNER and NOSTR BUNKER).

NIP-44 entered the NIPs repository on December 20, 2023, with the pull request “NIP44 encryption standard, revision 3”, proposed by Paul Miller with Jon Staab. The same day, the NIP states that version 2 of the format was audited by Cure53 in December 2023.

*The official title of the NIP is “Encrypted Payloads (Versioned)”. The name refers to an encryption format, not to a messaging protocol.*
