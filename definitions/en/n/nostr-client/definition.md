Application used to read and publish on Nostr, whether it runs on a phone, in a browser, or on a computer. The client has the user's events signed with their private key, sends them to several relays, subscribes to the events of followed accounts, verifies their signatures, and builds the feed it displays. In Nostr's architecture, the client does most of the work: relays store and retransmit events, with at most a few checks, and the base protocol does not provide for them to talk to each other.

The client talks to each relay over a WebSocket connection, which it keeps open for all its subscriptions. NIP-01 defines 3 message types for it to send: `EVENT` to publish an event, `REQ` to request events and subscribe to new ones, and `CLOSE` to end a subscription; other NIPs add more, such as `AUTH` or `COUNT`. Relays answer with `EVENT`, `EOSE`, `OK`, and other messages. A `REQ` carries one or more filters, which select events by identifier (`ids`), by author (`authors`), by kind (`kinds`), by tag (`#e`, `#p`...), by period (`since`, `until`), and by number (`limit`). The relay first returns the stored events that match, signals the end of this history with an `EOSE` message, then forwards new events live as long as the subscription stays open. After a publication, the relay answers with an `OK` message that accepts or rejects the event.

Let's take an example. Alice opens her client in the morning. It knows the list of accounts she follows, published in her follow list (an event of kind `3`). It sends each relay it knows a `REQ` whose filter asks for the notes (kind `1`) of these public keys since the day before. The answers arrive out of order and in duplicate, since Bob published the same note on 3 relays. The client discards duplicates using their identifier, rejects any event whose identifier does not match its content or whose signature does not match the announced public key, then sorts the rest by date to form the feed. When Alice replies to Bob, the client prepares an event of kind `1` with tags that point to Bob's note and public key, has it signed, and sends it in an `EVENT` message to several relays.

This client-side verification is what makes it possible to do without trusted relays. A relay can refuse an event, lose some, or hide some, but it cannot modify one without invalidating its identifier or signature (see NOSTR EVENT SIGNATURE). In his first presentation of Nostr, in November 2020, fiatjaf wrote that signatures are verified on the client side. The kind also tells the client how to interpret each event: NIP-23 thus specifies that a client centered on short notes should not be expected to display long-form articles.

The main difficulty for a client is knowing which relays to search for the events of each followed account, since they can be anywhere. Nostr's reference repository presents it as the hardest point of the protocol. The method described by NIP-65 is to read the relay list that each user publishes (kind `10002`), download their notes from their write relays, and send replies that mention them to their read relays, in addition to the write relays of the reply's author: this is the outbox model.

The private key does not need to reside in the client. The client can delegate signing to a Nostr signer: a browser extension that exposes `window.nostr` (NIP-07), an Android signing app (NIP-55), or a remote signer reached through relays (NIP-46). The client passes it the event to sign (with NIP-07 and NIP-46, without `id`, `pubkey`, or `sig`), and the signer returns it signed.

Many clients exist. They share the same identity and find the same data as soon as they query the same relays, since the data lives in the relays and not in the application. Damus is a client for iPhone, iPad, and Mac, Amethyst is a client for Android that also exists as a desktop version, and Gossip is a desktop client written in Rust. A user can switch clients or use several at once, with the same key.

*The term designates the application. It should not be confused with the signer, which keeps the key and performs the operations that use it: signing, encrypting, decrypting, and providing the public key.*
