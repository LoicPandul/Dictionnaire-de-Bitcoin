Shareable identifier defined by NIP-19 that encodes in Bech32 the public key of a Nostr user and, optionally, relays where their profile is most likely to be found. Whereas the `npub` contains only the key, the `nprofile` also indicates where to look for the person's profile.

The `nprofile` reuses the TLV structure of the `nevent`, with only 2 types of entries: type `0` contains the 32 bytes of the public key, and type `1`, optional and repeatable, the URL of a relay in ASCII. NIP-19 gives the example of an `nprofile` of 131 characters (72 bytes once decoded) that contains the key `3bf0c63fcb93463407af97a5e5ee64fa883d107ef9e558472c4eb9aaaefa459d` and 2 relays, `wss://r.x.com` and `wss://djbas.sadkb.com`. The same key written as an `npub` takes 63 characters: `npub180cvv07tjdrrgpa0j7j7tmnyl2yr6yr7l8j4s3evf6u64th6gkwsyjh6w6`. The 2 forms designate the same account; only the second says where to find it.

The `nprofile` is used notably to mention someone. NIP-27 describes the following scene: Bob writes a note and types `@mat`, his client suggests the matching profile, and Bob sees `@mattn` displayed. In the published event, the client has instead written `nostr:nprofile1…` (the `nostr:` prefix comes from NIP-21) and added a `p` tag with the key of the person mentioned. When Carol reads the note, her client decodes the `nprofile`, extracts the key and, if there are any, the relays, fetches the profile (the kind `0` event that contains the name and the image), then replaces the string with the name, with a link to the profile page. Outside of Nostr, NIP-21 also proposes placing an `nprofile` in a `<link rel="me">` tag of a web page to attribute it to a Nostr profile.

The relays in an `nprofile` are only a snapshot taken at the time of sharing. A user can change relays afterward, and the string already distributed will not follow. To learn the up-to-date relays of a person, a client relies on other mechanisms: the list of relays that the user publishes in a kind `10002` event (NIP-65), on which the outbox model rests, or the `relays` attribute that the domain of a NIP-05 identifier can return. The identity itself remains the public key: in the fields of an event, such as the `p` tag, and in NIP-05 responses, the key is always written in hexadecimal, and the `nprofile` appears only in displayed or shared text.

The `nprofile` has existed since NIP-19 was added to the NIP repository on December 16, 2022, at the same time as the `nevent`. Relay URLs were first encoded in UTF-8 there, then in ASCII from February 6, 2023.

*Not to be confused with the `npub`, which contains the key alone, nor with the profile itself, the kind `0` event published by the user.*
