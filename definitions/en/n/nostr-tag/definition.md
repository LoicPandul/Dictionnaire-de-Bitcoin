Array of strings placed in the `tags` field of a Nostr event to link it to something else (another event, a public key, an addressable event, a topic, a relay) or to add metadata to it. The protocol does not limit the number of tags, but each relay can set a cap. The first element of the array gives the tag name, the second its value, and the following ones additional information whose meaning depends on the tag. Because tags are part of the data hashed to obtain the event ID, they are covered by the author's signature just like the text.

NIP-01 defines 3 tags that keep the same meaning in all kinds:

* `e` refers to another event: `["e", <ID>, <recommended relay>, <author's public key>]`, the last 2 elements being optional;
* `p` refers to a user: `["p", <public key>, <recommended relay>]`, the relay being optional;
* `a` refers to an addressable event by its coordinate `<kind>:<public key>:<value of the d tag>` (see ADDRESSABLE EVENT), or to a replaceable event by `<kind>:<public key>:`, with an optional recommended relay.

The recommended relay gives the client an address at which to look for the referenced object, which helps find it when it is not on the reader's usual relays.

Tags are also used to query relays. By convention, a relay indexes all tags whose name is a single letter of the Latin alphabet, lowercase or uppercase, but only their first value. A client can then ask it, in a `REQ` filter, for all the events that carry a given tag with a given value. Let's take an example. Bob publishes a note. Alice replies to it: her client creates a kind `1` note that contains `["e", <ID of Bob's note>, "", "root"]` and `["p", <Bob's public key>]`. Charlie, who is viewing Bob's note, wants to see the replies: his client sends the relays the filter `{"kinds": [1], "#e": [<ID of Bob's note>]}` and receives Alice's note. For its part, Bob's client subscribes to the filter `{"#p": [<Bob's public key>]}` and can let him know that Alice mentioned him.

Beyond these 3 tags, the meaning of a tag depends on the kind and on the NIP that defines it. NIP-10 adds to a note's `e` tags an optional marker, `root` or `reply`, placed in 4th position (the author's public key then moves to 5th), which distinguishes the note that started a thread from the one being replied to directly, and asks that the authors concerned be added as `p` tags so that they are notified. A follow list (kind `3`, NIP-02) is just a sequence of `p` tags, each with an optional relay and petname. A relay list (kind `10002`, NIP-65) lines up `r` tags, marked `read` or `write`, or with no marker for a relay that serves both. The `t` tag carries a lowercase hashtag, the `d` tag the value that distinguishes addressable events from the same author and of the same kind, and a long-form article (NIP-23) stores its title, image, and summary in `title`, `image`, and `summary` tags. A deletion request (kind `5`, NIP-09) designates the events to delete through `e` or `a` tags.

What relays index remains a NIP-01 convention, and each relay chooses what it agrees to search. A tag whose name has several letters, such as `title`, is not covered by this convention: NIP-01 does not provide a `#` filter for it, and a relay such as strfry rejects the query. Likewise, only the first value of a tag is indexed: the recommended relay or the marker of an `e` tag cannot be searched.

NIP-01 as it was merged in May 2022 into the NIPs repository knew only the `e` and `p` tags, and announced that other tags would come later. The `a` tag appeared in February 2023, in NIP-33 and NIP-23, to designate what were then called parameterized replaceable events (now addressable); NIP-01 adopted it only in August 2023, when it absorbed NIP-33; in the proposal then under discussion, it was still called `i` a few days earlier.
