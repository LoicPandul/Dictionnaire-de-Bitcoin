Ability of a protocol rule update to remain compatible with earlier versions. It means the changes are designed so that old nodes (nodes running versions that predate the rule change) can still interact with the network and follow the chain with the most accumulated work. Old nodes must therefore reject neither the new blocks nor the new transactions.

Backward compatibility greatly reduces the probability that an update fragments the network, which avoids splitting nodes into subgroups on different chains. To remain compatible with earlier versions of the protocol, an update must make the existing rules stricter or introduce new ones. This principle defines a “soft fork”. Conversely, if an update relaxes existing rules or removes some of them, it is not backward compatible. It is then a “hard fork”.
