Set of specifications for storing files on plain HTTP servers, where each file is identified by the `SHA256` hash of its content and the user is identified by their Nostr key. Blossom is notably used to host the images, videos, and other files that Nostr posts reference by URL.

A file is called a blob ("binary data packet"). Its identifier is the `SHA256` of its bytes, and it forms the address: a Blossom server answers `GET /<sha256>` by returning the blob, with an optional file extension in the URL (`.png`, `.pdf`). Because the address is the hash of the content, the client can recompute the `SHA256` of what it receives and check that it is the right file, whichever server sent it. To upload, the client sends the bytes with `PUT /upload`; the server must not modify them, computes the `SHA256` over the exact bytes received, and responds with a JSON descriptor (`url`, `sha256`, `size`, `type`, `uploaded`).

Features are added through BUDs (Blossom Upgrade Documents) numbered BUD-00 to BUD-12: basic retrieval and upload, listing a user's servers, copying a blob from one server to another, media optimization, upload requirements, required payment, Nostr file metadata, reporting, URI scheme, authorization, and blob management. Only BUD-00 (the shared vocabulary) and BUD-01 (server requirements and blob retrieval) are mandatory; the others are optional.

Permissions go through Nostr. To upload or delete, the client presents, if the server requires it, an authorization token defined by BUD-11: a signed Nostr event of kind `24242`, which states in plain text what it authorizes (`Upload Blob`), carries a mandatory `expiration` tag, and a `t` tag that names the action (`get`, `upload`, `list`, `delete`, or `media`). The server thus identifies the user by their public key, with no account or password. These tokens are optional: a server can require them for some actions only.

The link with Nostr is completed by BUD-03 and NIP-B7. Each user can publish a replaceable event of kind `10063` that lists their Blossom servers, the most reliable first. Let's take an example. Alice posts a photo hosted at `https://cdn.example.com/<sha256>.png`, and that server later shuts down. Bob's client notices that the URL contains 64 hexadecimal characters before the optional extension, probably a `SHA256`; it reads Alice's kind `10063`, finds another server there, requests the same `<sha256>.png`, and checks the hash of the file it receives. A client that follows this procedure thus recovers the photo as long as one of Alice's servers still holds it, without the link in the post changing. The client must try to upload to at least the first server in the list and may send or copy the blob to the others.

This redundancy is not guaranteed: only the first server in the list is mandatory, each server sets its own retention policy, and it is up to the user to choose servers that keep their files.

The Blossom repository was created by hzrd149 on February 20, 2024. NIP-B7, which describes how Nostr clients use Blossom, was added to the NIPs repository on April 24, 2025. Blossom replaced NIP-96, another file storage interface for Nostr, added in January 2024: the NIPs repository declared it obsolete in favor of NIP-B7 on September 9, 2025.
