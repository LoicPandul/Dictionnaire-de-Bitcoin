One-time digital signature scheme, built from a simple hash function, that the computer scientist Leslie Lamport devised around 1975. The private key is a list of secret numbers, the public key is the list of their hashes, and signing a message amounts to revealing some of these secrets. Its security depends only on the hash function, which makes it resistant to quantum computers, but a key must sign only one message.

Alice, who wants to sign a message, starts by hashing it, for example with `SHA256`: this 256-bit hash is what she signs. To build her private key, she draws 512 random 256-bit numbers and arranges them in 256 pairs: in each pair, one secret corresponds to the value 0 of the bit of the same rank in the message hash, the other to the value 1. She then hashes each of these 512 secrets, and the list of the 512 resulting hashes forms her public key, which she can publish safely. To sign, Alice goes through the 256 bits of her message hash and, for each one, reveals the secret of the pair that matches its value. The signature is the sequence of these 256 secrets. Bob, who knows Alice's public key, hashes the message in turn, then hashes each secret received and checks that it lands, rank after rank, on the hash published for the value of the bit.

Let's take an example reduced to 4 bits. Alice draws 8 secrets: $a_0$, $a_1$, $a_2$, $a_3$ for the bits equal to 0 and $b_0$, $b_1$, $b_2$, $b_3$ for the bits equal to 1. Her public key is the list $H(a_0), \dots, H(a_3), H(b_0), \dots, H(b_3)$, where $H$ is the hash function. To sign a message whose hash, reduced to 4 bits, is `1011`, she reveals 4 of her 8 secrets:

```text
Bit rank             0     1     2     3
Secrets for a 0      a0    a1    a2    a3
Secrets for a 1      b0    b1    b2    b3
Message hash         1     0     1     1
Signature            b0    a1    b2    b3
```

Bob computes $H(b_0)$ and compares it with the hash published for a 1 at rank 0, then $H(a_1)$ with the hash published for a 0 at rank 1, and so on. The secrets $a_0$, $b_1$, $a_2$, and $a_3$ stay hidden.

To forge a signature, an attacker would have to either produce a secret whose hash appears in the public key without ever having seen it, that is, find a preimage, or find another message with the same hash as an already signed message. The security of the scheme therefore rests only on the properties of the hash function: its preimage resistance and second-preimage resistance. Against a hash function, the known quantum attack is Grover's algorithm, which speeds up the search for a preimage only quadratically: according to the Chaincode report (Anthony Milton and Clara Shikhelman, May 2025), it weakens `SHA256` without breaking it. RFC 8554 likewise notes that hash-based signatures would remain secure against a quantum computer. Conversely, as BIP-0360 points out, Shor's algorithm, run on a sufficiently powerful quantum computer, would make it possible to recover an ECDSA or Schnorr private key from its public key.

The scheme has 2 drawbacks, however. The first is single use: each signature reveals half of the secrets, so a key must be used only once. If Alice signs a second message with the same key, she reveals, at each rank where the 2 hashes differ, the other secret of the pair. In the example, after `1011` then `1001`, $a_2$ and $b_2$ are both public. The more messages a key signs, the more secrets an attacker knows, and the easier it becomes to find a message that Alice never signed but whose signature can be assembled from the secrets already published. On Bitcoin, BIP-0360 stresses that common practices such as RBF and CPFP would then risk revealing private keys.

The second drawback is size. With `SHA256`, the public key consists of 512 hashes of 32 bytes, or 16,384 bytes, and the signature of 256 secrets of 32 bytes, or 8,192 bytes, versus 64 bytes for a Schnorr signature, according to the comparison table in the Chaincode report. In August 2013, Gregory Maxwell saw this bulk as one of the reasons Bitcoin did not use Lamport signatures, while describing them as simple, fast, and intuitively secure against both classical and quantum computation.

Several schemes reduce these drawbacks. The Winternitz one-time signature signs several bits at once using hash chains, which shortens the signature. Merkle proposed in 1979 to combine many one-time keys to sign several messages with a single public key, which XMSS does by gathering them under the root of a Merkle tree. XMSS and LMS, described in RFC 8391 and RFC 8554, extend this work by Lamport, Diffie, Winternitz, and Merkle.

Bitcoin has never integrated the Lamport signature into its consensus rules, and Bitcoin Core contains no implementation of it. The idea nonetheless keeps coming back as a fallback against a quantum computer. As early as 2015, BIP-0141 (SegWit) cites it among the new script systems that a witness version number would allow adding by soft fork. In July 2021, Jeremy Rubin showed on the bitcoin-dev mailing list that with the `OP_CAT` opcode, a script could require, in addition to an ECDSA signature, a Lamport signature over the `HASH160` of that ECDSA signature, at the cost of about 8,860 bytes of script. BIP-0347, which proposes reactivating `OP_CAT` in Tapscript, takes up this use, since verifying a Lamport signature requires only hashing and concatenating values on the stack. It also points out the limit: placed in a Taproot script path, the Lamport signature probably does not suffice to protect the output, because a quantum attacker could spend it through the key path, and its authors know of no way to disable that path without a soft fork. P2MR (BIP-0360) proposes an output type close to P2TR, but without a key path.

Other work followed. In April 2024, Ethan Heilman described on the same mailing list a way to enforce a Lamport signature on a transaction without `OP_CAT`, relying on the variable length of ECDSA signatures, at the cost of a very large number of signatures. In June 2025, Conduition published a prototype of a Winternitz signature verified in Script with `OP_CAT`, whose spending transaction takes about 2,000 vB, less than Jeremy Rubin's Lamport scheme. The weakness of single use also serves as a tool: if someone signs 2 different messages with the same key, the 2 secrets of at least one pair become public, and a script can detect this to trigger a penalty, as Andrew Poelstra explained in May 2024. BitVM relies on this kind of preimage revelation to link the output of one operation to the input of the next.

The idea dates from around 1975, according to Lamport: in a Berkeley café, Whitfield Diffie described to him the problem of digitally signing a document, and Lamport immediately proposed this solution, which he presents as the first digital signature algorithm. Diffie and Martin Hellman described it in November 1976 in their paper *New Directions in Cryptography*, as a partial solution suggested by Lamport, and already proposed condensing the message with a one-way function before signing it. The technical report that Lamport wrote for SRI International in October 1979, *Constructing Digital Signatures from a One Way Function*, describes a different construction, which improves on a method published by Michael Rabin in 1978: the signer chooses 40 secret keys, deposits their 40 images in a trusted public register, and each signature reveals 20 of these keys, chosen according to the document. Lamport never published it in a journal: the text remained an SRI technical report.

*The dates given for this scheme vary by source: around 1975 according to Lamport, 1976 for its description by Diffie and Hellman, 1977 in the Chaincode report. Lamport's 1979 technical report describes a different construction.*
