Identifier of the form `name@domain`, similar to an email address, that makes it possible to receive a Lightning payment without sending an invoice in advance. A wallet that receives this identifier queries the domain's server to get a fresh invoice, then pays it. The Lightning Address is defined by LUD-16 of the LNURL protocol, not by a BOLT.

Let's take an example. Alice wants to pay Bob, whose address is `bob@example.com`. Her wallet sends a GET request to `https://example.com/.well-known/lnurlp/bob`. The server replies with the parameters of an LNURL-pay payment request (LUD-06): a callback URL (`callback`), the minimum and maximum amounts accepted, expressed in millisatoshis, and metadata. The metadata contains a `text/identifier` entry (or `text/email`, if the identifier is a real email address) that repeats the requested identifier. Alice chooses an amount within these bounds, and her wallet calls the callback URL with that amount. The server then returns a Lightning invoice, created for this payment, in the `pr` field. The wallet checks that the invoice amount is the one Alice chose, then pays it: the specification requires no further confirmation. Bob therefore only had to share his identifier in advance, and it can be displayed, printed, or read aloud.

LUD-16 imposes a stricter format than an email address: the name is limited to the characters `a-z0-9-_.`, in lowercase (and `+` if the service handles tags, as in `bob+shop@example.com`). The name `_` serves as the default identifier of a domain, so `@example.com` can be written in place of `_@example.com`, but this shortcut remains optional for the wallet. The Lightning Address project expects HTTPS, because a man-in-the-middle attack on this exchange affects real money. Receiving therefore requires an HTTP server that implements LNURL-pay, a Lightning node to create the invoices, and a domain name. Intermediary servers (bridge servers) can take the role of the HTTP server for anyone who does not want to run it. Sending only requires handling the request.

The process has limits that BIP-0353 points out. The domain's server knows who is paying, since the request reveals the sender's IP address, and it creates the invoice itself: the recipient depends on it. BIP-0353 puts these HTTP-based schemes among those that offer no succinct proof of the link between a name and a key, that expose the sender's IP address, and that rely on TLS certificate authorities. On November 16, 2023, according to the Optech newsletter of November 22, Bastien Teinturier proposed on the lightning-dev list email-like addresses based on offers (see BOLT-12), because in his view the existing standard creates several problems, including loss of privacy and the risk of invoice tampering.

BIP-0353, by Matt Corallo and Bastien Teinturier, answers this need: it stores payment instructions in a DNS TXT record, signed with DNSSEC, at the address `name.user._bitcoin-payment.domain`. It is meant to extend and replace the Lightning Address, with a ₿ prefix at display time (`₿name@domain`) to avoid confusion with an email address. A wallet can fall back to the Lightning Address if DNS resolution fails, but BIP-0353 recommends that it stop doing so once its scheme is widespread enough. In 2026, according to the Optech newsletter of August 21, Lexe handles BIP-0353 addresses, which also work as Lightning Addresses.

LUD-16 is a document in the lnurl/luds repository, created on August 1, 2021 when the text was split into separate documents, and its listed authors are Akumaigorodski, André Neves, and fiatjaf. On September 22, 2021, Optech reported that André Neves had announced the Lightning Address protocol, which wraps the LNURL-pay flow in email-like addresses. The project has since listed dozens of wallets that send to such addresses or offer to receive them, including Alby, Phoenix, BTCPay Server, and Electrum.

*Not to be confused with: a Lightning Address is not an on-chain Bitcoin address, nor an invoice, nor an offer (BOLT-12), and its format looks like an email address without being one.*
