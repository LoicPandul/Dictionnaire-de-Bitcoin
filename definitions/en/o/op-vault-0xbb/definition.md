Opcode `0xbb` proposed in BIP-0345 for Tapscript, replacing `OP_SUCCESS187`. It is the mechanism of a specialized covenant vault system, which makes it possible to impose a configurable delay before any spend, with the option of recovery in case of compromise.

The opcode consumes several items from the stack (from top to bottom): a `<leaf-update-script-body>` containing the body of the replacement script, a `<push-count>` indicating the number of additional data items, the corresponding data items, a `<trigger-vout-idx>` designating the index of the trigger output, a `<revault-vout-idx>` designating the index of an optional "revault" output (`-1` if there is none), and a `<revault-amount>` specifying the amount in satoshis to put back into the vault. From these items, the opcode builds a replacement script by prefixing the `<leaf-update-script-body>` with the supplied data, then verifies that the trigger output has a taptree identical to that of the current input, except for the leaf being executed, which is replaced by this new script. This Taproot leaf substitution preserves all the other leaves, including the recovery path via `OP_VAULT_RECOVER` (`0xbc`).

The opcode registers deferred checks to ensure that the value of the input is carried over in full between the trigger output and the optional "revault" output. This mechanism makes it possible to batch several vault inputs in the same transaction. On success, the value `0x01` is pushed onto the stack. BIP-0345 was closed and replaced by BIP-0443 (`OP_CHECKCONTRACTVERIFY`), which is more general.
