Unconfirmed transaction with an input that spends an output unknown to the node receiving it, because the parent transaction that creates that output is still missing. As long as the parent is neither in the node's mempool nor confirmed in the chain, the node cannot validate the transaction on its own: the orphan is not necessarily invalid, only incomplete from the point of view of that node.

This often happens without anyone having done anything wrong. Alice sends a parent transaction, then, a few seconds later, a child transaction that spends the change output of the first. The two propagate from node to node, but nothing guarantees that they arrive in that order at a given node. If the child arrives before its parent, validation fails with the result `TX_MISSING_INPUTS`. Rather than discarding the child, Bitcoin Core puts it in the orphanage, a reserve dedicated to orphans. The node then requests the missing parent, by its transaction ID (txid), from a peer that announced or sent it the orphan. As soon as that parent is accepted into the mempool (or, since version 32.0, confirmed in a block), the node retrieves the waiting children and revalidates them; those that pass leave the orphanage. If a block includes the orphan or makes it invalid, or if the last peer that had announced it disconnects, it is erased.

The node does not keep every orphan. It does not retain one whose parent has already been rejected (except for a fee rate that is too low), nor one whose weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 weight units), so that a peer cannot fill up memory with large transactions. Above all, the node cannot tell a true orphan from a faulty transaction that references nonexistent inputs: the Bitcoin Core code says so in a comment and derives tight limits from it. The orphanage also supports packages: when a parent is refused because its fee rate is too low, the node looks in the orphanage for a child received from the same peer and evaluates the package, which passes if the child pays enough to lift the parent, following the logic of one-parent-one-child package relay (see PACKAGE RELAY and CPFP).

These limits changed in 2025. Up to Bitcoin Core 29.0, the orphanage held at most 100 unique transactions by default (the `-maxorphantx` option, added by Gavin Andresen in 2014 and released with 0.9.3), and each orphan expired after 20 minutes. Bitcoin Optech Newsletter #341, of February 14, 2025, reports measurements by 0xB10C on his nodes: more than 10 million orphans evicted on some days, with a peak of more than 100,000 evictions per minute, more than 99% of which looked like transactions related to runestone mints. The same transactions were requested again, evicted at random shortly after, then requested again. Bitcoin Core 29.0 already downloads the missing parents from all the peers that announced the orphan. Version 30.0 (#31829) replaces the limit of 100 with global caps, shared out per peer: the number of announcements (unique per transaction and per peer), plus the number of inputs of each transaction divided by 10, does not exceed 3,000, and the total weight of unique transactions is limited to 404,000 weight units multiplied by the number of peers that have an announcement in the orphanage. When a global cap is reached, the node evicts the oldest announcements of the peer that consumes the most. No peer can thus cause the eviction of another peer's orphans, and orphans no longer expire. The `-maxorphantx` option has had no effect since 30.0 and was removed in 31.0. The `getorphantxs` RPC command lists the contents of the orphanage.

Orphan handling is a node behavior rule, not a consensus rule: two honest nodes can keep different orphans without splitting.

*Not to be confused with the orphan block (see ORPHAN BLOCK).*
