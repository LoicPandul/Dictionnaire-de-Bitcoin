Nostr event of kind `30000` to `39999` that relays replace by author, by kind, and by the value of its `d` tag, so that it is designated by a stable address rather than by its ID. An author can thus maintain several editable documents of the same kind, each under its own `d` tag. This mechanism carries long-form articles, many topical lists, calendar events, and Git repository announcements.

It extends the behavior of the replaceable event, with one more criterion. For each combination of kind, public key, and `d` tag value, a relay must keep the most recent event, according to the `created_at` field, and may discard earlier versions. These 3 elements form the event's coordinate, written `<kind>:<public key>:<d value>`. The ID, for its part, changes with every edit, since it is the hash of the public key, the date, the kind, the tags, and the content: a link to the ID always points to a specific version, whereas a link to the coordinate follows the updates.

Let's take an example. Alice publishes an article on Nostr. Her client creates an event of kind `30023` (long-form article, NIP-23) with the tag `["d", "multisig-2026"]`, the text in Markdown in `content`, and a title in a `title` tag. A week later, she fixes a typo: her client republishes the entire event with the same `d` tag and a more recent `created_at`. Relays replace the old version with the new one. Bob, who wants to cite the article, uses an `["a", "30023:<Alice's public key>:multisig-2026"]` tag; to share a link, he uses an naddr, which encodes this coordinate and, optionally, relays where the article can be found. In both cases, readers should in principle get the corrected version. If Alice publishes a second article under a different `d` tag, it coexists with the first.

The main uses are long-form articles (kind `30023`, see Nostr long-form content) and the sets of NIP-51, which allow several lists of the same type: groups of followed accounts (kind `30000`), groups of relays (kind `30002`), or bookmark categories (kind `30003`). The kinds table of the NIPs repository lists many others, such as calendar events (NIP-52), live streams (NIP-53), Git repository announcements (NIP-34), or classified listings (NIP-99). To delete an addressable event, a deletion request (kind `5`, NIP-09) designates it with an `a` tag, and relays are then expected to erase all its versions up to the date of the request.

NIP-33, the original text, specified that a missing `d` tag, or one with no value, is equivalent to the empty string, and that only the first `d` tag counts. As with replaceable events, replacement remains a convention of NIP-01 that each relay applies in its own way: a relay that does not apply it may still serve an old version, and a client does well to hide the extra versions it receives, as NIP-23 recommends for articles.

The mechanism comes from NIP-33, added to the NIPs repository on January 4, 2023 by Semisol under the name *parameterized replaceable events*, the parameter being the `d` tag. The `naddr` entities and the `a` tag that refers to them appeared in February 2023. NIP-33 was merged into NIP-01 on August 13, 2023, and fiatjaf then renamed these events *addressable events* on August 20, 2024.
