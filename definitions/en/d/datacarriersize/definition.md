Bitcoin Core configuration option that sets the maximum size, in bytes, of the `OP_RETURN` output scripts a transaction may contain for the node to relay and mine it. It is a policy rule, specific to each node, not a consensus rule. It counts only `OP_RETURN` outputs, used to record arbitrary data in the blockchain, and leaves out the other ways of placing data in it. It goes with `-datacarrier`, which enables or disables this relay.

The node applies the limit when accepting a transaction into its mempool. It goes through the outputs of the transaction, spots those whose script begins with `OP_RETURN` followed by plain data, and subtracts the size of each entire script, `OP_RETURN` and push opcodes included, from a budget equal to the value of `-datacarriersize`. If an output exceeds what remains of the budget, the node rejects the transaction with the reason `datacarrier`. Since Bitcoin Core 30.0, this budget is shared among all the `OP_RETURN` outputs of the transaction, which can therefore contain several. With `-datacarrier=0`, the budget is zero: any `OP_RETURN` output makes the transaction nonstandard. The value in force can be read from the `maxdatacarriersize` field of the `getmempoolinfo` command, which is 0 if `-datacarrier` is disabled.

Let's take an example, with the old limit of 83. Alice publishes an 80-byte message in an `OP_RETURN` output: the script is 1 byte for `OP_RETURN`, 2 for the push opcodes, and 80 for the message, for a total of 83 bytes, and nodes relay it. With an 81-byte message, the script is 84 bytes and default nodes reject the transaction. The figure of 83 script bytes thus corresponds to the 80 bytes of data that developers usually talk about. Alice can still send her transaction directly to a miner: the limit governs only the relay by nodes that apply it, not the validity of blocks.

The option dates back to Bitcoin Core 0.10.0: Luke Dashjr added it in October 2014, with a default of 40 bytes of data. Flavien Charlon raised it to 80 bytes in November 2014, in Bitcoin Core 0.11.0. Since 0.12.0, the limit applies to the entire script: 83 bytes, which is the same 80 bytes of data plus 3 of header. This ceiling stayed in place until 2025.

In 2025, the default value became the subject of a debate. In spring, a discussion on the bitcoin-dev mailing list, then on a Bitcoin Core pull request, concerned raising or even removing this limit. Pieter Wuille argued that a standardness rule can hardly prevent the confirmation of data transactions created by well-funded organizations, which send them directly to miners, and that blocks are full with or without them. Jason Hughes replied that raising the limit would make it easier to store arbitrary data on node operators' computers, some of it probably illegal in the jurisdiction of the operator. In answers on Bitcoin Stack Exchange, picked up by Optech in September 2025, Antoine Poinsot and Ava Chow argued for removal rather than a raise to 160 bytes: according to Poinsot, the default limit creates a bad incentive; large miners already work around it, and future uses cannot be guessed.

Gregory Sanders's pull request #32406, merged on June 9, 2025, changed the default from 83 to 100,000. Since the maximum size of a standard transaction is 100,000 vB, this value effectively removes the limit. The Bitcoin Core 30.0 release notes, published in October 2025, state that the old ceiling can be restored with `-datacarriersize=83`. Pull request #32406 also marked both options as deprecated. Mike Schmidt's pull request #33453, with a commit by Anthony Towns, merged on September 30, 2025 and included in 30.0, reversed this deprecation: many users want to keep these options, and the deprecation plan remained unclear. Bitcoin Knots keeps 83 as the default in its version v29.4.2.knots20260508.

A node that keeps 83 therefore continues to filter what it relays, whereas a node at the 30.0 default no longer filters, in practice, the size of `OP_RETURN` outputs. For the use of the word spam in these exchanges, see the SPAM entry.

*The name comes from "data carrier". Not to be confused with a consensus limit, nor with a limit on witness data: the option counts only `OP_RETURN` outputs.*
