Bitcoin Core wallet in which scripts are described by output script descriptors rather than by a set of keys: each descriptor determines which scripts the wallet owns and how to derive them. Since Bitcoin Core 23.0, it is the wallet type created by default and, since 30.0, the only one the software loads. The descriptor syntax is described in the entry on output script descriptors.

Bitcoin Core's older wallet, known as the legacy wallet, keeps a set of keys (and, where applicable, imported scripts) and implicitly infers the corresponding scripts and addresses from them. The release notes for version 0.21.0 draw a consequence from this: in a legacy wallet, `IsMine`, the function that decides whether an output belongs to the wallet, could recognize the P2WPKH script corresponding to a known key even though the wallet had never produced that address. With descriptors, the wallet's set of scripts is enumerated in advance, and the wallet recognizes only the scripts of its descriptors, including those derived ahead of time that it has not yet handed out.

Let's take an example. Alice runs `createwallet "alice"` on a mainnet node. In recent versions, the software draws a random key to use as the seed, derives a master key from it, and creates 8 descriptors: 4 output types (P2PKH, P2SH-P2WPKH, P2WPKH, and P2TR), each in an external version (receiving addresses) and an internal version (change addresses). The external P2WPKH descriptor is stored as `wpkh(xpub…/84h/0h/0h/0/*)`, with the master extended public key (`listdescriptors` displays it with the fingerprint and the account key), where `84h`, `0h`, and `0h` are the usual derivation levels, and `/*` denotes a series of numbered scripts. The P2TR descriptor uses `86h` and `tr()`. On a test network, the second level is `1h`. The wallet keeps the master private key and these descriptors in its database, an SQLite file, whereas legacy wallets use Berkeley DB. For each descriptor, it keeps an index of the next address to hand out and derives 1,000 scripts ahead by default (the `-keypool` option), so that it can recognize payments received on addresses it has not yet shown, for example after restoring an old backup.

Descriptors also serve as an interface. The `listdescriptors` RPC displays a wallet's descriptors, `importdescriptors` adds some to an existing wallet (only descriptors that include their checksum can be imported), and `createwalletdescriptor` creates some for a given address type, one external and one internal by default. A descriptor wallet created without private keys (the `disable_private_keys` option) works as a watch-only wallet (see the entry on watch-only wallets): it does not mix descriptors with and without private keys, and the `include_watchonly` option of the RPCs has had no effect since 30.0. The `getwalletinfo` RPC returns a `descriptors` field, always true since 30.0, where legacy wallets no longer load. The `importmulti` and `dumpprivkey` RPCs, specific to legacy wallets, disappeared along with them in 30.0.

The descriptor wallet settled into Bitcoin Core gradually. Descriptors first entered the software in version 0.17.0, for the `scantxoutset` RPC. Andrew Chow (Ava Chow) had native wallet support merged on April 27, 2020 (PR 16528), and version 0.21.0 offered it as an experimental option, with Berkeley DB replaced by SQLite. Version 23.0 made it the default type and added a `tr()` descriptor. Version 24.0.1 introduced the `migratewallet` RPC, which converts a legacy wallet. With 26.0, `createwallet` refuses to create a legacy wallet without the `-deprecatedrpc=create_bdb` option, and 30.0 removes the creation and loading of legacy BDB wallets. The migration, which backs up the wallet before converting it, had a flaw in versions 30.0 and 30.1: if it failed on an unnamed wallet, the entire `wallets` directory could be erased. Version 30.2 fixes this flaw.

*Not to be confused with descriptors themselves, which are a notation (BIP-0380) that other software can also use, nor with a watch-only wallet.*
