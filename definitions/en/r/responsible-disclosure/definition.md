Practice in which the person who discovers a vulnerability in software first reports it privately to its developers, so that it is fixed before the details become public. Bitcoin Optech describes it as a way of reporting a vulnerability to developers, affected users, and the public that helps limit the damage. It contrasts with immediate publication, which gives attackers time to exploit the vulnerability before users have been able to protect themselves.

In the Bitcoin ecosystem, the process is simple. Let's take an example. Alice, a security researcher, finds a remote crash in a node. She writes to the project's security address: for Bitcoin Core, it is security@bitcoincore.org, with public keys for exchanging sensitive information. The developers confirm the problem, prepare a fix, release a version, and then, at a later stage, publish the security advisory that describes the vulnerability, often with a CVE identifier.

The timing of the publication of details is set by a policy. The one published on the Bitcoin Core website sorts each report into 4 severity levels: critical, high, medium, and low. A low-severity vulnerability is detailed 2 weeks after the release of a major version that fixes it. A medium- or high-severity one is detailed 2 weeks after the end of life of the last affected version, roughly a year after the first major version containing the fix. For any vulnerability under embargo, a pre-announcement giving the number of vulnerabilities fixed and their severity is published 2 weeks before the details, along with a new major version. Critical vulnerabilities fall outside this framework: they call for a case-by-case procedure. If a vulnerability can be found with minimal effort, for example with a simple request to an LLM, the policy instead provides for releasing a fix as soon as possible, for every maintained major version, without applying these delays.

Developers can also delay the release of the code. In August 2026, Core Lightning withheld its source code for 14 days after publishing the binaries of its security release 26.06.7, to slow the reverse engineering of the fixes. Reproducible builds can then be used to verify that the amd64 binaries match the code.

The case of CVE-2018-17144 shows a two-stage disclosure. Reported on September 17, 2018 as a simple denial of service by a reporter whom Bitcoin Optech identifies as Awemany, the vulnerability turned out to also allow the creation of bitcoin outside the issuance schedule. The fix appeared on September 18 in Bitcoin Core 0.16.3, with disclosure of only the denial of service, while the developers warned miners and companies and kept the inflation quiet to leave time to update. On September 20, a post on a public forum revealed the full impact, and Bitcoin Core published its full disclosure. According to that advisory, more than half of the hashrate had updated by then and no exploitation attempt was known.

Bitcoin Optech maintains on its website a list of the responsible disclosures it has reported, from 2015 to 2026, notably for Bitcoin Core, LND, Core Lightning, Eclair, LDK, btcd, and BTCPay Server. It specifies that the list is incomplete, since other disclosures are not cited or are not yet public, and that it does its best to judge how responsible each one was. In September 2026, for example, it reports Erick Cestari's disclosure of a denial of service in Core Lightning, fixed in version 25.09, released a year earlier, in September 2025. Replacement cycling, disclosed in October 2023, is another example.

*Responsible disclosure does not mean secret disclosure: the vulnerability is meant to be documented publicly once it is fixed.*
