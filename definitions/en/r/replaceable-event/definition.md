Nostr event of which relays need to keep only the most recent version for a given author and a given kind. Events of kind `0` (profile), `3` (follow list), and `10000` to `19999` (mute lists, bookmarks, relay lists...) are replaceable. Each newer publication replaces the previous one, which suits data that a user updates rather than accumulates.

The rule comes from NIP-01: for each combination of public key and kind, a relay must keep the most recent event, and may discard earlier versions. The most recent one is determined by the `created_at` field. If 2 versions carry the same timestamp, the relay should keep the one whose ID comes first in lexical order. When a client requests, for example, `{"kinds": [0], "authors": [<public key>]}`, the relay should return only the latest version, even if it has kept several.

Let's take an example. Alice follows 200 accounts and decides to follow Bob. Her client does not publish an “Alice follows Bob” event: it republishes her entire follow list, a kind `3` event that now contains 201 `p` tags. NIP-02 specifies that each new list overwrites the previous ones, and that it should therefore contain all the entries. Relays that receive the new list replace Alice's old list, and a client that queries one of them then retrieves the up-to-date list in a single request.

The main uses are the profile (kind `0`), whose content gives the user's name, description, and image; the follow list (kind `3`); and the standard lists of NIP-51, such as the mute list (kind `10000`), pinned notes (kind `10001`), or bookmarks (kind `10003`). The relay list of NIP-65 (kind `10002`), which announces the relays where the user writes and those where they read their mentions, is also a replaceable event: it is the list read by a client that follows the outbox model. To designate a replaceable event in an `a` tag, its coordinate `<kind>:<public key>:` is written ending with a colon, since it has no `d` tag.

This storage mode has its limits. Replacement is a convention of NIP-01 that not all relays apply identically: nothing obliges a relay to purge old versions, so it may still serve one. Since the most recent version is the one with the highest `created_at`, a client whose clock is behind publishes a list that relays ignore, and a client whose clock is ahead publishes a list that prevails over legitimate later updates. A client that republishes a list from an incomplete copy, for example because it did not find the latest version on its relays, erases the missing entries in the process. Finally, an author has only one event per kind; to have several, the author needs an addressable event, distinguished by its `d` tag.

The generalization comes from NIP-16, proposed in May 2022 by Semisol, which defined the `10000` to `19999` range and ephemeral events. Kinds `0` and `3` already behaved this way: in the May 2022 versions, NIP-01 allowed a relay to delete a public key's old profiles as soon as it received a new one, and NIP-02 already said that each new follow list overwrites the previous ones. NIP-16 was merged into NIP-01 on August 13, 2023, which has since gathered all the kind ranges.

*Not to be confused with the addressable event, which is also replaceable but by author, kind, and `d` tag, or with the ephemeral event, which relays are not supposed to store.*
