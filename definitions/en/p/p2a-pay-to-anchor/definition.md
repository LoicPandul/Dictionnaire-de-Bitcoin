Acronym for *Pay-to-Anchor*. Output type whose script is `OP_1 <0x4e73>` and which anyone can spend without a signature or witness data. It serves as an anchor for a transaction signed in advance: once that transaction is broadcast, the party who wants it confirmed faster spends the anchor in a child transaction that pays the fees, following the CPFP principle.

The need comes from contract protocols such as Lightning. Alice and Bob sign transactions long before broadcasting them and cannot guess the fee rate the network will require on the day one of them has to go out. With an anchor, the signed transaction stays valid as is and the fees are settled later, at the going rate. The anchor outputs deployed in Lightning today reserve each anchor for the key of one of the two parties; anyone can sweep it only after 16 blocks (see ANCHOR OUTPUTS). P2A removes the key: a third party that holds no secret, a watchtower for example, can also bid.

The script is 4 bytes long: `OP_1` announces a SegWit version 1 witness program, then a length byte (`0x02`) precedes the 2-byte program, `0x4e73`. These two bytes were chosen so that the `Bech32m` address spells “fees”: `bc1pfeessrawgf` on mainnet, `tb1pfees9rn5nz` on the public testnets, `bcrt1pfeesnyr2tx` on regtest. It is not a Taproot output (see SEGWIT V1), which requires a 32-byte program: for consensus, a version 1 program of any other length has no rule of its own, and the spend is accepted without the witness being examined. P2A therefore adds no consensus rule. It relies only on the relay policy of nodes.

Let's take an example. Alice and Bob share a Lightning channel with zero-fee commitments (described below), and their commitment transaction contains a P2A output. Alice broadcasts it: it pays no fees and will not be confirmed in time. Alice creates a child transaction that spends the P2A output, adds one of her inputs to pay the fees, and sets their amount so that the rate of the package, parent and child together, reaches the target. She submits the two transactions as a package (see PACKAGE RELAY), for example with Bitcoin Core's `submitpackage` command, and miners using Bitcoin Core's block template evaluate them together (see CPFP - CHILD PAYS FOR PARENT). Bob could have done it in her place: the anchor belongs to no one in particular.

Two policy rules govern the spend. The input that spends a P2A must contain no witness: a transaction that adds one is nonstandard, which prevents a third party from changing its witness transaction ID (wtxid) by slipping in useless data. A P2A nested in a P2SH is not spendable in a standard way either: the relay rejects the transaction, even though consensus accepts it. As for the amount, the dust threshold of P2A is 240 sats at Bitcoin Core's default rate, or 3,000 sats per kvB (see DUST LIMIT), against 294 sats for a P2WPKH output: below it, the transaction that creates the output is not relayed. A separate rule, ephemeral dust, has allowed an output below this threshold, even at 0 sat, since Bitcoin Core 29.0, in a zero-fee transaction whose every child must spend that output; with the default settings, such a transaction enters the mempool only as a package with its child, and in version 3 (see TRUC). The two ideas together were called ephemeral anchors (see EPHEMERAL ANCHORS).

Because anyone can spend the anchor, anyone can attach to it a large, low-fee-rate child that hinders the confirmation of the parent (see TRANSACTION PINNING). BIP-0433 advises pairing it with TRUC transactions when in doubt, since they limit the size and number of children (see TRUC), while specifying that there is no intrinsic dependency between the two. According to the Optech newsletter of August 9, 2024, Peter Todd also pointed out on bitcoin-dev that an attacker can attempt replacement cycling against a transaction that uses a P2A (see REPLACEMENT CYCLING); according to Optech, only a counterparty stands to profit from it, and the countermeasures already deployed in Lightning also work against this variant.

Greg Sanders formulated the idea. On October 18, 2022, he presented ephemeral anchors on bitcoin-dev: a bare `OP_TRUE` output, spendable with an empty witness, to be spent in a package of v3 transactions (which became TRUC transactions) whose parent pays no fees. P2A takes up this principle with a 4-byte segwit script, slightly bigger than the bare `OP_TRUE` but without its flaw: the ID of the child transaction can no longer be modified by a miner. Greg Sanders' PR #30352, opened on June 27, 2024 and merged on August 2, 2024, makes it standard in Bitcoin Core 28.0; such a spend was previously nonstandard. BIP-0433, an informational BIP by Gregory Sanders, still in Draft status as of October 24, 2026, describes the output type.

On the Lightning side, the specification of zero-fee commitment channels (BOLTs #1228, merged on May 4, 2026) gives both parties the same P2A anchor. Its value is taken from that of the outputs too small to be included in the transaction, capped at 240 sats, and can therefore be zero. The commitment transaction no longer has to pay fees, and the `update_fee` message disappears from this type of channel.

*Not to be confused: P2A is the output type, BIP-0433 is the document that describes it, and ephemeral anchors is the name once given to the combination of P2A and ephemeral dust, two rules that are now separate.*
